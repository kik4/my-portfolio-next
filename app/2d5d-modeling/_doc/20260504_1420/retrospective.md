# 2D5D Modeling Tool 振り返り (2026-05-04)

## このドキュメントの目的

`app/2d5d-modeling/` で「2D アニメの嘘を取り込んだ擬似 3D キャラクターモデル」を作るために、複数の方式を試してきた。最新の v4（2D パーツ + 3D アンカー付きビルボードグループ）まで実装した上でツールを実際に触ってみた結果、**根本問題が解決していない**ことが分かったので、その所感と、ここに至るまでの設計遍歴を残しておく。次に再挑戦するときに同じ袋小路を踏まないための備忘録。

## 1. ツールを触っての所感（結論）

> **2D だけのときに発生していた「ジンバルロック的な問題」は、土台（ルートグループ）だけ 3D にしても、2D パーツについては解決しなかった。この試行も失敗だったように思える。**

### 何が問題か

- v4 ではパーツを **完全な 2D（basePoints + 2x3 アフィン）** とし、ルートグループの 3D アンカーをカメラに対して常時ビルボード化することで「3D 空間に置かれた 2D 絵」を表現した
- しかし「正面の目を、横から見ても少し正面寄りに見せたい」のような 2D アニメ的な嘘は、**結局パーツ自身の view keyframe の補間で実現するしかない**
- 補間の対象は basePoints と 2x3 アフィン。ここでアフィンが回転を含むと、2 つの keyframe の中間角度で「無回転」を経由する経路に落ち、どの角度から見ても妙な姿勢になる瞬間が出る
- view 補間方式を Gaussian RBF（正規化）→ Gaussian RBF（exact、base-relative）→ Delaunay + 重心座標 と 3 段階に変えても、**この症状は緩和されたが解消はしなかった**
- 結局「2D パーツの view 軸補間」というアプローチを取る限り、パーツの絵を成立させる回転・歪みのパラメトリックな補間は (yaw, pitch) 平面上で気持ちよく繋がらない。土台が 3D 化しても 2D パーツ自身がぶら下げる補間問題は変わらない

### この試行を失敗とみなす理由

- 「全角度で気持ちよい絵」を出すために、ユーザー（自分）はキーフレームを **密に置かないと崩れる**運用を強いられる
- パーツ単位の affine を 6 成分独立で線形補間する設計を変えない限り、回転角の中点問題は構造的に消えない
- 仮にアフィンを decompose して回転だけ slerp 風にしても、剪断や非一様スケールが入った瞬間に decompose の選び方で結果が分岐し、編集体験が予測不能になる
- 三角形分割で「3 keyframe しか効かない」を保証してもなお、**3 keyframe の中間で起きる回転中点問題**は残る（むしろ「離れた keyframe が混ざるからボヤけて見えていた」のがクッキリ可視化されただけ）

つまり今回の取り組みは、

- **直接の症状（pitch 違いの keyframe が yaw 操作中に混ざる）には有効**だった
- **根本問題（2D パーツに対する view 軸パラメトリック補間そのものの限界）には無力**だった

## 2. これまでの開発経緯（要約）

ブランチ `2d5d_modeling` の commit を年代順に追うと、大きく 5 世代の方式を試したことが分かる。

### 第 1 世代: 単発のビルボード貼り付け（〜 2026-04 序盤）

- スプライトを 3D 空間に置き、カメラに対してビルボード化するだけ
- yaw 範囲ごとに別画像をスワップする発想
- spec: `20260411_2231/spec.md`、`20260417_2320/...`、`20260420_1400/...`
- 廃案理由: 連続性なく切り替わる。中間視点で破綻

### 第 2 世代: 楕円体配置 + 2D ベジェ顔（2026-04 中旬）

- 顔メッシュを楕円体近似し、その表面に 2D ベジェのパーツをマッピング
- spec: `20260421_0108/spec.md`、`f46fa10` で「3D-placement spec superseding the billboard approach」
- view RBF（球面距離 + Gaussian）導入はこの時期 (`f670166`)
- 廃案理由: 楕円体に貼り付くと「顔のシルエットを keyframe ごとに変える」嘘がつけない。形状が固定の 3D に縛られる

### 第 3 世代: コントロールメッシュ + Catmull-Clark（2026-04 末）

- 顔形状を制御メッシュで定義し Catmull-Clark で滑らかに分割。パーツも頂点に対する重み補間で配置
- spec: `20260429_1638/spec.md`、commit: `3fe3140` 〜 `281eb6c`
- 廃案理由: 制御メッシュの手数が多く、「アニメの嘘」を入れるには 3D 構造が硬すぎる

### 第 4 世代: view-driven（2026-04-30 〜 2026-05-02）

- spec: `20260430_0130/spec.md`、progress: `20260502_2106/progress.md`
- 「キーフレームごとに頭シルエット込みで全体を作り、view (yaw, pitch) と anim (任意パラメータ) の二軸 RBF で補間する」設計
- パーツは 3D 空間でレイキャストして頭メッシュに貼り付ける placement 方式（`PartPlacement`）
- 多くの編集 UI（PointEditor、HeadCurveEditor、AnchorGizmo、マルチビュー、Undo/Redo）はこの世代で揃った
- 廃案理由: パーツがレイキャストで「頭表面に縛られる」ため、2D アニメの嘘（前から見たときの目の配置）が頭メッシュ形状に引きずられる

### 第 5 世代: v4 二層モデル（2026-05-03 〜 2026-05-04、本セッション）

- spec: `20260503_1316/spec.md`
- パーツは **純 2D**（basePoints + 2x3 アフィン）、グループは 3D アンカー + 完全ビルボード
- ルートグループだけが 3D アンカーを持ち、子グループは親の 2D 平面内で重ねる
- view 軸補間: 当初 Gaussian RBF（正規化、`d53abc3`）→ exact RBF（`0449939`）→ base-relative（`7b82054`）→ Delaunay + 重心座標（`1f03806`）
- 編集 UI: 2D アフィンギズモ（`31c0342`）、ツリー DnD（`6b38f8a`）、ミラー複製（`e7d04ba`）など
- 触ってみた結果が **本ドキュメント冒頭の所感**

## 4. 次にやり直すなら

「やり直す」と決めたわけではないが、次に同じ問題に挑むときに考えておくべき方向性をメモしておく。優劣は付けない。

### 方向 A: パーツも 3D に持ち上げる

- パーツの形状を **薄い 3D メッシュ**として定義し、view keyframe では「メッシュをどう曲げるか」のリグ（FFD / blend shape）だけを補間する
- 2D アニメの嘘を入れるための「形状が時間ではなく視点で変わる」性質はリグの補間で表現
- 利点: 2D 軸 → 2D 軸の補間という不安定な構図から抜けられる
- 欠点: 編集 UI が大変。「絵として描く」感覚から離れる

### 方向 B: keyframe 補間ではなく keyframe 切替 + 局所モーフ

- yaw/pitch を範囲（4〜8 視点）に区切り、各範囲で **1 つの keyframe を選んで使う**。範囲境界だけ短いクロスフェードでモーフ
- view 軸の連続パラメトリック補間そのものを諦める
- 利点: 中間角度の崩れが「クロスフェード幅の中だけ」に閉じる
- 欠点: 滑らかさが要る用途には合わない

### 方向 C: 補間対象をアフィンではなく「ホモグラフィ + 形状」に変える

- 2D ホモグラフィなら、4 点対応で「視点 A の絵を視点 B にどう写すか」が決まる
- view keyframe を「視点における 2D 絵そのもの」と定義し、補間は経路ではなく **写像合成**で行う
- 利点: 中点で「無回転に見える」ような線形補間特有の崩れが起きにくい
- 欠点: 設計・実装ともに重い。ホモグラフィの平均化は非自明

### 方向 D: そもそも 2D スプライト + 機械学習で view 補間

- 視点ごとの絵だけを描いて、間は学習ベース（Neural Radiance Field / 3D Gaussian Splatting / 任意の view-conditioned 生成）で埋める
- 範囲が広がるが本プロジェクトの趣旨（手作りの嘘を入れる）とは離れる

## 4.5. 次に挑むならこの方向（2026-05-04 セッション末の結論）

セッションの最後で議論し、次回再挑戦するときの第一候補として合意した方針を残しておく。

### コア発想: 「3D 制御点 + 辺 + 面 → 投影 → 2D で結ぶ」

- パーツの形状を **3D 空間の制御点 + 辺 + 面（小規模メッシュ）** で持つ（2D の basePoints + 2D アフィン ではなく）
- 描画時に各 3D 制御点をカメラで投影して 2D 点を得る
- 投影後の 2D 点を **辺で結んで線画にし、面で塗る**。シルエット（輪郭線）は視点ごとに「前向き面と後ろ向き面の境界エッジ」を抽出して描く
- 凸形状（球・楕円球）でも凹形状（鼻先・耳・口の隙間）でも、同じデータ構造で扱える

この時点で view 軸の補間（RBF / Delaunay / アフィン中点）は **不要**になる。カメラが回れば点の見かけ位置が幾何的に正しく動くので、これまで延々と悩んだ「2 つの keyframe の中間角度で姿勢が崩れる」回転中点問題は **構造的に発生しない**。

### ただし純粋 3D 投影だけでは「視点ごとの嘘」が出せない

3D 制御点を投影するだけだと、視点に対して絵は連続写像になる。「正面では大きく前向きの目、横では小さく後ろ向きの目」のような **視点ごとに絵がジャンプする嘘** は表現できない。これは本ツールの本来の動機（横顔でも正面側の目が見える等のアニメ的嘘）と矛盾する。素直な 3D モデルに近づくだけになる。

### 解決策: 3D 制御点を view keyframe で動かす（v4 とのハイブリッド）

- 基本は 3D 投影（カメラで自然に視点が変わる）
- それに加えて、各 3D 制御点の位置自体を view keyframe（yaw, pitch）で補間して揺らす
- 補間対象は **3D 点の位置（3 成分の連続値）のみ**。アフィン 6 成分のように姿勢の中点問題が出る要素を持たない

### この方式の何が違って、何が同じか

| 項目 | v4（廃案） | 次案（3D メッシュ + view 補間） |
|---|---|---|
| パーツの本体 | 2D basePoints + 2x3 アフィン | 3D 制御点 + 辺 + 面（小規模メッシュ） |
| 視点を変える操作 | パーツ内 view keyframe の補間で疑似回転 | カメラで投影、視点変化は幾何的に自動 |
| 「ジンバルロック的問題」 | 発生（アフィン回転の中点問題） | 発生しない（3D 投影は幾何的に正しい） |
| 視点ごとの嘘 | 2D アフィンの keyframe で表現 | 3D 制御点位置の view 補間で表現 |
| view 軸補間で扱うもの | 2x3 アフィン 6 成分 + 2D shape の各点 | 3D 点の位置 3 成分のみ（辺・面トポロジは固定） |
| 輪郭線の出方 | 2D shape の外周をそのまま描く | 視点ごとに前向き面 / 後ろ向き面の境界エッジを抽出 |
| 凹形状の表現 | 2D shape を凹に描けば成立（投影前提なので簡単） | 面の前後判定で自然に出る |

要は v4 が「パーツに 2D 絵を持って 2D アフィンで疑似 3D 化する」設計だったのを、「パーツに **3D メッシュ** を持って投影で 2D 絵にする」設計に逆転させる。view keyframe の概念は残すが、その対象は 3D 点位置に限定される（辺・面のトポロジは view 軸では変えない）。

### 編集 UX の見通し

- 制御点は 3D 空間に配置するので、編集 UI は v4 の AnchorGizmo（drei TransformControls）方式が流用できる
- ただし「正面ビューでドラッグして xy 編集、側面ビューでドラッグして z 編集」のように **2D ビューで編集できる経路**を残しておかないと、3D 直接ドラッグだけでは深さの把握が難しい（過去の Catmull-Clark 版で痛感した点）
- マルチビュー（4 固定 + 1 メイン）は流用できる。ミニビューを 2D 編集ビューとして兼用する手もある
- view keyframe で 3D 点を揺らすときは、各 keyframe で「3D 点列のスナップショット」を持つ。辺・面のトポロジは全 keyframe 共通（v4 の shapeTopology 同期と同じ発想）
- **デバッグ可視化を最初から組み込む**: メッシュのエッジ線描画、面の法線方向の矢印、winding 方向の表示。Catmull-Clark 版で詰まったのは「シェーダ的に法線が逆だった」類の実装ミスで、可視化があれば即座に判別できる種類の不具合だった。設計が原理的にダメだったわけではない

### 過去のメッシュ系試行（Catmull-Clark）との違い

第 3 世代（Catmull-Clark）は「3D 制御メッシュを編集する」点で次案と似ているが、廃案理由は次案では当てはまらない:

- **Catmull-Clark の廃案理由**: 制御メッシュ → 細分化メッシュという階層が複雑、編集 UX が硬すぎる、3D 整合性に縛られて 2D 嘘が入れにくい
- **次案で違う点**: 細分化レイヤなし（持つメッシュがそのまま描画対象）、view keyframe で 3D 点位置を視点ごとに動かせるので 2D 嘘が直接表現できる、レイキャスト配置のような硬い拘束もない
- 過去に法線・winding まわりで詰まった件は、メッシュ表示・wireframe・法線可視化で発見できる種類の問題。設計的な障害ではなく実装デバッグの問題

### 残る検討事項（未決）

- メッシュの面構成（三角形ベース / 四角形ベース / 混合）
- エッジを「常に描く線」として明示するか、シルエット判定に任せるか（両方持つのが現実的）
- シルエット判定: 各エッジの両側の面の前後判定（dot(normal, viewDir) の符号反転）。境界エッジ（片側にしか面がない）は常にシルエット
- 線で結ぶときの曲線形式（投影後 2D で Catmull-Rom スムージングをかけるか、直線多角形のまま描くか）
- 閉領域の塗り（earcut で 2D 三角化はそのまま流用可、ただし投影後にやる）
- 描画の前後関係: パーツ単位で z-sort するか、面単位で z-buffer を使うか、`layerIndex` を残すか
- アニメ（anim 軸）は 3D 点位置への delta として残す？それともパラメータ駆動のリグに置き換える？
- 視点ごとの嘘がどれくらい強くかけられるか実機検証必要。例えば「正面で目を大きく、横で小さく」を 3D 点位置の view 補間でやると、結局 v4 と同じく **3D 点の view 補間が回転中点的な問題を再導入しないか** は確認が要る（位置だけなら大丈夫そうだが、点が多いと集合として姿勢の中点問題に化ける可能性は残る）
- 凹形状で視点によってシルエットループが分裂する場合の扱い（例: 鼻が顔の輪郭から飛び出す瞬間で 1 ループ → 2 ループに切り替わる）

### 流用候補（v4 から残せそうなもの）

- 輪郭線シェーダ（backface hull, world-space inflate）— シルエットエッジ抽出と併用するか、こちら一本で済むか要検証
- マルチビュー（MultiView + Scene + 固定 4 視点 + メインインタラクティブ）
- Undo/Redo（useHistory）
- localStorage 永続化 + JSON I/O
- ortho カメラ + OrthoZoom
- AnchorGizmo（3D 点ドラッグの基本機構）
- グループ階層（PartTree + DnD reparent + ⇄ ミラー複製）
- shapeTopology（点追加/削除を全 keyframe に伝播）の発想は、メッシュトポロジ編集に応用可能

廃棄:
- 2D アフィン中心の編集 UI（AffineGizmo2D）
- 2D shape の PointEditor（3D メッシュ用に作り直し）
- view 軸補間ロジック（viewRbf.ts / Delaunay 三角形分割）— 3D 点位置補間は別実装
- 頭メッシュの楕円断面スイープ生成（HeadMesh + headMeshBuild + HeadCurveEditor）— パーツがメッシュを持つので「土台メッシュ」の特別扱いは不要になる可能性が高い（ただし頭部もパーツの 1 つとしてメッシュで持てば自然）
