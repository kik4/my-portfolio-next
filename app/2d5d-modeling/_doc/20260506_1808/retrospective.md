# 2D5D Modeling Tool v5 第一段階 振り返り (2026-05-06)

## このドキュメントの目的

[20260506_1513/spec.md](../20260506_1513/spec.md) で定義した v5 第一段階（3D メッシュエディタ、2D 嘘なし）を実装し、デフォルト形状で触ってみた結果、**3D メッシュ → 投影 → シルエット**という経路自体に **頂点数が少ないと視点変化でシルエットがパクパクと不連続に変化する**という構造的な問題が見つかった。これを次の挑戦に持ち込まないための備忘録。

## 1. 触っての所感（結論）

> **3D メッシュは頂点が少ないとシルエットがボコボコで、投影後に Catmull-Rom で滑らかに繋いでも、視点を回すたびに「シルエットを構成する頂点集合」自体がジャンプするため、輪郭の形が不連続にパクパク変化する。**

### なぜ起きるか

- 3D メッシュのシルエット = 「両側の面の前後判定が異なるエッジ」の集合
- 視点を ε だけ回すと、**ある面の前後判定が反転する瞬間**がやってくる
- そのとき、シルエットを構成するエッジ集合が離散的に切り替わる（例: 頂点 1, 3, 5, 6, 8, 10 → 1, 3, 4, 6, 8, 10）
- 切り替わった瞬間、シルエット曲線の形が **不連続にジャンプ**
- スクリーン空間 Catmull-Rom は「その時点のシルエット頂点列を滑らかに繋ぐ」だけなので、頂点集合のジャンプには追従できない

メッシュの頂点を増やすほどジャンプの幅は小さくなり、見た目では滑らかになるように見える。しかしそれは「頂点数を上げて誤魔化す」ことでしかなく、本ツールが spec.md:241 で目標としている「**少ない制御点で滑らかな顔の輪郭が作れる**」とは構造的に相反する。

## 2. v5 第一段階で達成したこと

ジャンプ問題を除けば、第一段階の機構は揃った。MS1〜MS4 と追加の面塗り改善まで完了。

### 編集機構（MS1）
- 3D 制御点 + 辺 + 三角形面のメッシュ編集（追加 / 削除 / 移動 / 法線反転）
- 4 ペインビュー（正面 / 側面 / 上面 / 3D 操作、最大化トグル）
- 各ペインで点ドラッグ（2D ペインは平面拘束）
- 単一選択 + Shift クリック複数点選択
- デバッグ可視化（wireframe / 法線方向 / winding 表裏色分け、各 ON/OFF）

### 投影プレビュー（MS2 + MS3）
- シルエットエッジ抽出（透視投影対応 = 各面重心からカメラへの方向で判定）
- シルエット edges → 頂点ループに連結
- 奥のエッジを depth occlusion で隠す（手前面 fill mesh で深度書き込み）
- スクリーン空間 Catmull-Rom（centripetal）スムージング
- **面塗りはスムージング後のシルエット曲線を earcut で三角化**（線と塗りが完全一致）

### 階層・履歴・永続化（MS4）
- PartTree（グループ + パーツ、表示/非表示、HTML5 native DnD reparent + 循環チェック）
- ノードエディタ（パーツの色/線/名前、グループの名前）
- Undo/Redo（200 ステップ、ドラッグ中は preview / 確定で commit）
- localStorage 自動保存 + JSON エクスポート/インポート + デフォルトに戻す

### デフォルト形状の遍歴
- 立方体: 各面が真にフラットで対角線問題なし、最初の動作確認に最適
- UV-球（廃案）: 「四角ポリゴンが厳密には非平面 → 内部対角線がシルエット判定される」問題が出た。`quadDiagonals` フィールドを足して suppress する案も実装したが、ユーザー側の編集 UX（quad 概念の認知負荷）と本問題は別次元の話で、根本解決にならなかった
- 正二十面体（現行）: 12 点 / 30 辺 / 20 三角形面、すべて真にフラット。対角線問題は原理的に発生しない。ただし頂点数が少ないため、ジャンプ問題が顕在化した

## 3. 何が原理的問題で、何が実装の問題だったか

### 原理的問題（頂点数を増やすしかない）
- **シルエット頂点集合の離散ジャンプ**（本ドキュメントの主題）
- 凸形状の境界エッジは法線符号が反転するエッジのため、面が増えるほど境界エッジ候補は増え、視点変化での切り替わりも細かくなる

### 実装で対処できる / した問題
- 透視投影への対応（カメラ forward 共通だと真正面で詰む → 各面重心からカメラへのベクトルで判定）
- 奥のエッジが透ける（手前面の depth-only / fill で z-buffer に書き込み）
- 塗りが線とずれる（earcut で投影後のスムージング曲線を三角化）
- 非平面 quad の対角線がシルエット入りする（正二十面体に切り替えで回避）

実装側はおおむね気持ちよく動いている。原理的問題だけが残っている。

## 4. retrospective.md（前回）との関係

[20260504_1420/retrospective.md:180](../20260504_1420/retrospective.md) で次の予兆が書かれていた:
> 視点ごとの嘘がどれくらい強くかけられるか実機検証必要。例えば「正面で目を大きく、横で小さく」を 3D 点位置の view 補間でやると、結局 v4 と同じく **3D 点の view 補間が回転中点的な問題を再導入しないか** は確認が要る（位置だけなら大丈夫そうだが、点が多いと集合として姿勢の中点問題に化ける可能性は残る）

今回の発見はこれと別の次元の問題：
- 前回の懸念: **3D 点の位置を view 補間したときに姿勢の中点問題が出るか**（view keyframe 機構を載せたあとの話）
- 今回の発見: **view keyframe を載せる前の段階で、3D メッシュ → 投影 → シルエットという経路自体がパクパクする**

つまり、**view keyframe を入れる前にもう 1 つ詰めるべき問題が見つかった**。

## 5. 次の方向性（未決、議論用メモ）

優劣はつけない。次に挑むときに考える材料として残す。

### 方向 a: メッシュ細分化（Loop subdivision など）
- 制御メッシュは少ない頂点のまま、描画用に細分化したメッシュを使う
- ジャンプ幅は小さくなる（頂点 4 倍で隣接する頂点間角度が 1/2 倍）
- 編集体験は「少ない制御点で」を保てる
- 第 3 世代（Catmull-Clark）の廃案理由は「制御メッシュ → 細分化メッシュという階層が複雑、編集 UX が硬すぎる」だったが、今回は「**滑らかなシルエットが目的**」と最初から目的が明確なので、編集 UX を硬くしなくても済む可能性がある
- 過去 Catmull-Clark で詰まった法線・winding 系の不具合は実装デバッグの問題（[20260504_1420/retrospective.md:169](../20260504_1420/retrospective.md) で明記済み）

### 方向 b: 曲面表現（暗黙曲面 / 楕円球 / metaball / SDF）からシルエット抽出
- メッシュではなく **暗黙曲面**（数式で定義される曲面）からシルエットを取る
- 楕円球なら制御点 = 中心 + 半径 3 つ で滑らかな輪郭
- 顔のような複雑形状は metaball / SDF の合成で
- ジャンプは原理的に発生しない（曲面が連続だから）
- 編集 UX が大幅に変わる

### 方向 c: シルエット曲線を直接持つ
- パーツに「3D 制御点メッシュ」と別に「**3D 空間で定義された輪郭曲線**（Catmull-Rom スプラインの 3D 制御点列）」を持たせる
- 描画時: シルエットは輪郭曲線を投影、塗りはその内側
- メッシュは法線判定や深度テストの参照用、または廃止
- 「投影で自動的に出すシルエット」という前提自体を捨てる
- view keyframe を載せる際は **シルエット制御点の位置を view 補間** = 3D 点位置補間と同じ仕組み
- 本ツールの動機（2D アニメ的な嘘 = 絵としての輪郭をいじる）と相性が良い

### 方向 d: 投影しない（前回 retrospective の C / D に近い）
- ホモグラフィや学習ベース等。今回の問題ではなく前回検討の続き

### 方向 e: 諦めて頂点を多くする
- 単純に正二十面体を 1〜2 段階細分化してデフォルトにし、「少ない制御点」目標を緩める
- 編集体験は劣化する（点が多くなる）が、機構は今のまま使える

## 5.5. 整理: 「3D 化の本来の動機」と「シルエットを自動生成する動機」は別物

ここまでの経緯を後から雑談で整理して気付いたこと。次回再開時に最初に思い出すべき話なので別節を立てる。

### 経緯のトポロジ

1. **出発点**: Live2D 的な「2D 制御点 + 角度パラメータで変形 = 疑似 3D」
2. **ぶつかった壁 (v4)**: 線形補間は中央付近の角度では機能するが、**ピッチ極（真上 / 真下）では「ただの回転」が必要**で、補間では再現できない。極まで連続させようとすると破綻する
3. **3D 化の動機**: 「制御点を 3D に上げれば、極の回転は **カメラ回転で自動的に出る**」。補間という不確かな機構に頼らずに極まで対応できる
4. **現在の壁 (v5)**: 3D メッシュからシルエットを取ると、頂点が少ないと視点でパクパクする
5. **冷静な再認識**: 「3D メッシュからシルエットを作る」は本筋ではない

### 動機 (α) と (β) の分離

- **(α) 補間問題を 3D 化で解く**: 3D 制御点をカメラ回転させれば、極の回転は自動で正しく出る。補間に頼らず幾何で解く。**動機としては筋が良い**
- **(β) 3D 制御点から自動でシルエットを作る**: ここが現在うまくいっていない。**副産物にすぎない**。捨てて良い

### この整理に基づく方向 c の最有力化

方向 c（シルエット曲線を直接持つ）は (α) を取って (β) を捨てる具体案そのもの。

- パーツに「3D 制御点列」を持たせる（メッシュではない、ただの 3D 点列）
- それらを **シルエット曲線の制御点**として扱う（順序付き、閉じている）
- 描画: 3D 制御点列をカメラで投影 → 投影後の 2D 点列を Catmull-Rom で結ぶ → 内側を塗る
- 視点変化: カメラ回転で 3D 制御点が投影される位置が変わる → シルエットが幾何的に正しく追従。**極まで連続**
- 離散ジャンプ問題: **発生しない**（曲線の制御点集合は固定で、ただ位置が動くだけ）
- メッシュ（面 / 法線 / winding）は **要らない**

### 方向 c の引き換えに手放すもの

- 「メッシュとしての表面」が無い: 凹凸のある立体的な絵を「立体構造として」表現できない
- ただし本ツールの目的は「**そう見える絵を作る**」こと（2D アニメ的な嘘）であって 3D 整合性ではない。シルエット内に別パーツ（鼻、目）を z 順で重ねれば対応できる（Live2D もそれ）
- パーツ内部の「線として残したいエッジ」（鼻筋、口の隙間）は別の **内部曲線**として持てばよい

### 方向 c の 2D 嘘との整合性

view keyframe で「3D 制御点の位置」を補間する → これは前 retrospective ([20260504_1420/retrospective.md:180](../20260504_1420/retrospective.md)) で予兆されていた話そのもの。3D 点位置の補間なら姿勢の中点問題が起きにくい（位置の中点は単に中点）。シルエット曲線の制御点が 3D 点列なので、view keyframe 機構を素直に載せられる。

### 暫定の最有力候補: 方向 c

複数候補のうち、**方向 c が現在の最有力候補**。理由：

- ツールの動機（絵としての嘘）と直接整合する
- 離散ジャンプ問題を構造的に回避できる
- (α) の利益（極の回転をカメラに任せる）はそのまま取れる
- view keyframe / 2D 嘘の機構と整合する
- 流用候補: マルチビュー、Undo/Redo、PartTree、永続化、Catmull-Rom 実装、3D 点ドラッグ機構（PointGizmo / PointDragger2D）

### それでも他方向を試す理由が残るケース

- 方向 a (細分化): メッシュ的な凹凸を本当に持ちたい場合
- 方向 b (暗黙曲面): 「楕円球 + metaball」で頭の大づかみを取り、c を上に重ねる構成は十分ありえる
- 方向 d (投影しない): 前 retrospective での検討続き、c がうまく行かない場合の保険

## 6. 何を保留にして、いつ判断するか

### 保留にする
- v5 第一段階の「実際に顔を組んでみる」評価（spec.md:241 の最初の判定軸）。シルエットがパクパクする状態では正当な評価にならない
- 2D 嘘（view keyframe）の検討。シルエット安定性が解決していない上に載せても、評価軸がさらに混ざる

### 次に判断したいこと
- **方向 c を採るかの最終判断**（5.5 節の整理に基づく暫定の最有力候補）
- 方向 c を採る場合の設計詳細:
  - パーツのデータ構造（3D 制御点列 + 内部曲線群 + 各曲線の閉/開フラグ + 線色 / 塗り色）
  - 編集 UX: 4 ペインの 3D 制御点ドラッグはほぼ流用可、ただし「曲線として」見せる UI が要る
  - 凹閉曲線の自己交差や複数ループの z 順
  - 顔の大づかみ（楕円球 / metaball）と曲線パーツの組み合わせを取るか（方向 b との併用）
- 方向 c を採らない場合は a / b / d / e のどれかを試す
